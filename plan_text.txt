SECTION 01
Project Overview
Cipher6 (HexaConnect) is a privacy-focused social communication app where users connect through
Instagram-style usernames
— not phone numbers or account numbers. The app provides 
            end-to-end encrypted voice calls and chat messages between friends.
🎯 What Users Can Do
Create an account with a unique username
Search for other users by username
Send and accept friend requests
Make E2EE voice calls with friends
Send E2EE chat messages to friends
See friends' online/offline status
Edit their profile (name, bio, avatar)
🔒 Core Principles
Username is king
— sole identifier
Privacy by design
— E2EE everything
Friends-only
— must be mutual friends to call/chat
Ultra-low bandwidth
— ~18 MB/hour calls
No phone number
— no email required
Server is blind
— never sees plaintext

3.5 — E2EE Voice Calls
⚠️ Requirement
Both users
must be mutual friends
. Server enforces this check before relaying any call request.
Call Flow
1. User A taps 📞 on @alice's card in Home screen
2. Server checks friendship → relays CALL_REQUEST to @alice
3. @alice sees incoming call overlay: "@darkphoenix is calling..."
4. @alice taps [Accept] → WebRTC handshake begins
5. SDP Offer/Answer exchanged via server (signaling)
6. ICE candidates exchanged → direct P2P connection
7. Audio flows directly between devices (NOT through server)
8. Either user taps [End Call] → cleanup → return to Home

Online vs Offline
User A sends message to @alice:
  ├── @alice ONLINE  → message sent via WebRTC DataChannel (P2P direct)
  └── @alice OFFLINE → message stored encrypted on server (blind mailbox)
                       → delivered when @alice logs in next
                       → deleted from server after delivery

SECTION 04
Database Schema
Database Engine:
SQLite
(server-side)  |  Password Hashing:
Argon2id
Table 1: users
CREATE TABLE users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    username TEXT UNIQUE NOT NULL,        -- '@darkphoenix' (primary identifier)
    display_name TEXT NOT NULL,           -- 'Alex Chen'
    bio TEXT DEFAULT '',                  -- 'Privacy enthusiast 🔒'
    avatar_index INTEGER DEFAULT 0,      -- Index into preset avatar list
    password_hash TEXT NOT NULL,          -- Argon2id hash
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    last_seen TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_username ON users(username);
CREATE INDEX idx_display_name ON users(display_name);
Table 2: friends
CREATE TABLE friends (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,            -- Who SENT the request
    friend_id INTEGER NOT NULL,          -- Who RECEIVED the request
    status TEXT NOT NULL DEFAULT 'pending',  -- 'pending' | 'accepted' | 'blocked'
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(id),
    FOREIGN KEY (friend_id) REFERENCES users(id),
    UNIQUE(user_id, friend_id)
);

CREATE INDEX idx_friends_user ON friends(user_id, status);
CREATE INDEX idx_friends_friend ON friends(friend_id, status);
How Mutual Friendship Works:
User A sends request to User B:
  → INSERT (user_id=A, friend_id=B, status='pending')

User B accepts:
  → UPDATE status='accepted' WHERE user_id=A AND friend_id=B
  → INSERT (user_id=B, friend_id=A, status='accepted')
  → Two rows = mutual friendship

Either removes friend:
  → DELETE WHERE (user_id=A AND friend_id=B)
  → DELETE WHERE (user_id=B AND friend_id=A)
  → Both rows removed
Table 3: pending_messages
CREATE TABLE pending_messages (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    sender_id INTEGER NOT NULL,
    recipient_id INTEGER NOT NULL,
    encrypted_content TEXT NOT NULL,      -- AES-256-GCM encrypted (server can't read)
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (sender_id) REFERENCES users(id),
    FOREIGN KEY (recipient_id) REFERENCES users(id)
);
Table 4: login_attempts
CREATE TABLE login_attempts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    username TEXT NOT NULL,
    ip_address TEXT NOT NULL,
    attempted_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    success BOOLEAN DEFAULT FALSE
);

🔒 Security Rule
The server
enforces
that
CALL_REQUEST
and
CHAT_MESSAGE
can only be sent between
mutual friends
(status = 'accepted'). Strangers cannot contact you.
Connection Lifecycle
1. Client connects to WebSocket
2. Client sends LOGIN or REGISTER
3. Server validates → adds to connection map {username: websocket}
4. Server notifies all online friends: FRIEND_STATUS (is_online: true)
5. Server sends pending friend requests + pending messages
6. Heartbeat ping every 30 seconds
7. On disconnect:
   → Remove from connection map
   → Update last_seen in database
   → Notify online friends: FRIEND_STATUS (is_online: false)
   → If in a call: send HANG_UP to peer

Critical Gaps Addressed
These 5 gaps were identified and addressed in the implementation plan to ensure the app works in real-world conditions.
Gap 1: 🔴 Android Kills Calls When App Minimized
Critical — Without This, App Is Unusable
On Android 14+, pressing Home during a call kills microphone access within seconds.
Solution: Foreground Service
<!-- AndroidManifest.xml -->
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_PHONE_CALL" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_MICROPHONE" />
<uses-permission android:name="android.permission.MANAGE_OWN_CALLS" />

<service
    android:name=".CallForegroundService"
    android:foregroundServiceType="phoneCall|microphone"
    android:exported="false" />
Plus: Wake Lock (
wakelock_plus
) + Audio Focus management.

Gap 3: 🟡 Messages to Offline Peers
User A sends message → Peer B is offline?
  ├── YES → Server stores message in SQLite (encrypted, temp)
  │         → When Peer B reconnects, server delivers pending messages
  │         → Server deletes messages after delivery confirmation
  └── NO  → Message goes directly via P2P DataChannel (normal)
Server never sees plaintext — messages encrypted by sender with AES-256-GCM before storage.
Gap 4: 🟡 Credential Storage
Store
JWT session token
in
flutter_secure_storage
(NOT the password)
Enable
EncryptedSharedPreferences
on Android for hardware-backed encryption
On app restart: read stored token → validate with server → auto-login
On token expiry: prompt re-login
Gap 5: 🟡 Edge Cases
Edge Case
Solution
