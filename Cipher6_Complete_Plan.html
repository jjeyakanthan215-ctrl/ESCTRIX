SECTION 01

Project Overview

Cipher6 (HexaConnect) is a privacy-focused social communication app where users connect through Instagram-style usernames — not phone numbers or account numbers. The app provides end-to-end encrypted voice calls and chat messages between friends.

🎯 What Users Can Do

  • Create an account with a unique username
  • Search for other users by username
  • Send and accept friend requests
  • Make E2EE voice calls with friends
  • Send E2EE chat messages to friends
  • See friends' online/offline status
  • Edit their profile (name, bio, avatar)

🔒 Core Principles

  • Username is king — sole identifier
  • Privacy by design — E2EE everything
  • Friends-only — must be mutual friends to call/chat
  • Ultra-low bandwidth — ~18 MB/hour calls
  • No phone number — no email required
  • Server is blind — never sees plaintext

Core Features

3.1 — Authentication (Username-Based)

Registration

Username3-20 chars, lowercase letters + numbers + underscores only
Display NameRequired, any text, can be changed later
PasswordMinimum 8 characters, strength indicator shown
Confirm PasswordMust match password
Server-sideArgon2id hash (memory=65536, time=3, parallelism=4)
On SuccessReturns JWT token + user profile data

Username Validation Rules

RuleDetail
Length3–20 characters
CharactersLowercase letters, numbers, underscores only (a-z, 0-9, _)
UniquenessServer enforces UNIQUE constraint
CaseStored and searched case-insensitively (lowercased on registration)
ReservedCannot use: admin, system, cipher6, support, null, undefined
DisplayShown with @ prefix everywhere (e.g., @darkphoenix)
ImmutableUsername cannot be changed after registration

Login

  • Username + password → server verifies Argon2id hash
  • Returns JWT + profile + pending friend requests + pending messages
  • Login throttling: 5 failed attempts = 5 minute lockout
  • JWT stored in flutter_secure_storage (EncryptedSharedPreferences)
  • Auto-login on app restart (validate stored token)

  • Case-insensitive matching

Friend Request Flow

User A taps [+ Add] on @alice's search result ↓ Server creates: friends(user_id=A, friend_id=B, status='pending') ↓ If @alice is online → instant push notification via WebSocket ↓ @alice sees request in Activity screen ↓ @alice taps [✓ Accept] ↓ Server creates MUTUAL friendship (both directions) ↓ Both users see each other in Friends list immediately ↓ Both can now call and chat with each other

3.5 — E2EE Voice Calls

⚠️ Requirement

Both users must be mutual friends. Server enforces this check before relaying any call request.

Call Flow

1. User A taps 📞 on @alice's card in Home screen 2. Server checks friendship → relays CALL_REQUEST to @alice 3. @alice sees incoming call overlay: "@darkphoenix is calling..." 4. @alice taps [Accept] → WebRTC handshake begins 5. SDP Offer/Answer exchanged via server (signaling) 6. ICE candidates exchanged → direct P2P connection 7. Audio flows directly between devices (NOT through server) 8. Either user taps [End Call] → cleanup → return to Home

Call Features

  • Mute/unmute microphone
  • Speaker toggle (earpiece ↔ speakerphone)
  • Call timer (HH:MM:SS)
  • Connection quality indicator (green/yellow/red)
  • Foreground Service — call stays alive when app minimized

3.6 — E2EE Chat Messages

Encryption Details

SpecValue
AlgorithmAES-256-GCM

Online vs Offline

User A sends message to @alice: ├── @alice ONLINE → message sent via WebRTC DataChannel (P2P direct) └── @alice OFFLINE → message stored encrypted on server (blind mailbox) → delivered when @alice logs in next → deleted from server after delivery

SECTION 04

Database Schema

Database Engine: SQLite (server-side)  |  Password Hashing: Argon2id

Table 1: users

CREATE TABLE users ( id INTEGER PRIMARY KEY AUTOINCREMENT, username TEXT UNIQUE NOT NULL, -- '@darkphoenix' (primary identifier) display_name TEXT NOT NULL, -- 'Alex Chen' bio TEXT DEFAULT '', -- 'Privacy enthusiast 🔒' avatar_index INTEGER DEFAULT 0, -- Index into preset avatar list password_hash TEXT NOT NULL, -- Argon2id hash created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, last_seen TIMESTAMP DEFAULT CURRENT_TIMESTAMP ); CREATE INDEX idx_username ON users(username); CREATE INDEX idx_display_name ON users(display_name);

Table 2: friends

CREATE TABLE friends ( id INTEGER PRIMARY KEY AUTOINCREMENT, user_id INTEGER NOT NULL, -- Who SENT the request friend_id INTEGER NOT NULL, -- Who RECEIVED the request status TEXT NOT NULL DEFAULT 'pending', -- 'pending' | 'accepted' | 'blocked' created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, FOREIGN KEY (user_id) REFERENCES users(id), FOREIGN KEY (friend_id) REFERENCES users(id), UNIQUE(user_id, friend_id) ); CREATE INDEX idx_friends_user ON friends(user_id, status); CREATE INDEX idx_friends_friend ON friends(friend_id, status);

How Mutual Friendship Works:

User A sends request to User B: → INSERT (user_id=A, friend_id=B, status='pending') User B accepts: → UPDATE status='accepted' WHERE user_id=A AND friend_id=B → INSERT (user_id=B, friend_id=A, status='accepted') → Two rows = mutual friendship Either removes friend: → DELETE WHERE (user_id=A AND friend_id=B) → DELETE WHERE (user_id=B AND friend_id=A) → Both rows removed

Table 3: pending_messages

CREATE TABLE pending_messages ( id INTEGER PRIMARY KEY AUTOINCREMENT, sender_id INTEGER NOT NULL, recipient_id INTEGER NOT NULL, encrypted_content TEXT NOT NULL, -- AES-256-GCM encrypted (server can't read) created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, FOREIGN KEY (sender_id) REFERENCES users(id), FOREIGN KEY (recipient_id) REFERENCES users(id) );

Table 4: login_attempts

CREATE TABLE login_attempts ( id INTEGER PRIMARY KEY AUTOINCREMENT, username TEXT NOT NULL, ip_address TEXT NOT NULL, attempted_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, success BOOLEAN DEFAULT FALSE );

Server Protocol — All Message Types

WebSocket server on 0.0.0.0:8765  |  Connection map: {username: websocket}

Rate Limits

ActionLimit
Registrations5 per hour per IP
Login attempts5 per 5 minutes per username
Messages30 per minute per user
Search queries10 per minute per user
Friend requests20 per hour per user

Authentication Messages

TypeDirectionPurpose
REGISTERClient → Server{username, display_name, password} → validate → return JWT
LOGINClient → Server{username, password} → return JWT + profile + pending data

Social / Friend Messages NEW

TypeDirectionPurpose
SEARCH_USERSClient → Server{query} → return matching users with friend status
FRIEND_REQUESTClient → Server{target_username} → create pending → notify if online
FRIEND_REQUEST_NOTIFYServer → ClientPush: someone sent you a friend request
FRIEND_ACCEPTClient → Server{request_id} → accept → create mutual friendship
FRIEND_DECLINEClient → Server{request_id} → delete pending request
FRIEND_REMOVEClient → Server{friend_username} → remove mutual friendship
FRIEND_LISTClient → ServerRequest full friends list with online/offline status
FRIEND_STATUSServer → ClientPush: a friend came online or went offline
GET_PROFILEClient → Server{username} → return user's public profile
UPDATE_PROFILEClient → Server{display_name, bio, avatar_index} → update own profile

Calling Messages UPDATED

TypeDirectionPurpose
CALL_REQUESTClient → Server{target_username} → must be mutual friends → relay
CALL_ACCEPTClient → ServerAccept incoming call → trigger WebRTC handshake
CALL_REJECTClient → ServerReject incoming call → notify caller
OFFERClient → ServerRelay WebRTC SDP offer to peer
ANSWERClient → ServerRelay WebRTC SDP answer back
ICE_CANDIDATEClient → ServerRelay ICE candidates between peers
HANG_UPClient → ServerEnd call → notify peer
BUSYServer → ClientTarget is already in a call

Chat Messages

TypeDirectionPurpose
CHAT_MESSAGEClient → Server{target_username, encrypted_content} → must be friends → relay or store
🔒 Security Rule

The server enforces that CALL_REQUEST and CHAT_MESSAGE can only be sent between mutual friends (status = 'accepted'). Strangers cannot contact you.

Connection Lifecycle

1. Client connects to WebSocket 2. Client sends LOGIN or REGISTER 3. Server validates → adds to connection map {username: websocket} 4. Server notifies all online friends: FRIEND_STATUS (is_online: true) 5. Server sends pending friend requests + pending messages 6. Heartbeat ping every 30 seconds 7. On disconnect: → Remove from connection map → Update last_seen in database → Notify online friends: FRIEND_STATUS (is_online: false) → If in a call: send HANG_UP to peer

SECTION 08

Critical Gaps Addressed

These 5 gaps were identified and addressed in the implementation plan to ensure the app works in real-world conditions.

Gap 1: 🔴 Android Kills Calls When App Minimized

Critical — Without This, App Is Unusable

On Android 14+, pressing Home during a call kills microphone access within seconds.

Solution: Foreground Service

<!-- AndroidManifest.xml --> <uses-permission android:name="android.permission.FOREGROUND_SERVICE" /> <uses-permission android:name="android.permission.FOREGROUND_SERVICE_PHONE_CALL" /> <uses-permission android:name="android.permission.FOREGROUND_SERVICE_MICROPHONE" /> <uses-permission android:name="android.permission.MANAGE_OWN_CALLS" /> <service android:name=".CallForegroundService" android:foregroundServiceType="phoneCall|microphone" android:exported="false" />

Plus: Wake Lock (wakelock_plus) + Audio Focus management.

Gap 2: 🟡 Incoming Calls When App Closed

ApproachHow It WorksLimitation
V1: WebSocket-onlyApp must be running to receive callsCalls missed when app killed
V2: FCM + ConnectionServicePush notification wakes appRequires Firebase setup
Recommendation

Start with V1 (WebSocket-only). Add FCM push in a later version.

Gap 3: 🟡 Messages to Offline Peers

User A sends message → Peer B is offline? ├── YES → Server stores message in SQLite (encrypted, temp) │ → When Peer B reconnects, server delivers pending messages │ → Server deletes messages after delivery confirmation └── NO → Message goes directly via P2P DataChannel (normal)

Server never sees plaintext — messages encrypted by sender with AES-256-GCM before storage.

Gap 4: 🟡 Credential Storage

  • Store JWT session token in flutter_secure_storage (NOT the password)
  • Enable EncryptedSharedPreferences on Android for hardware-backed encryption
  • On app restart: read stored token → validate with server → auto-login
  • On token expiry: prompt re-login
